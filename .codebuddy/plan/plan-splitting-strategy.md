# 大型计划拆分实施方案

## 方案概述

当需求规模较大时，multi-plan 需要采用**计划拆分策略**来提升可执行性和可维护性。

---

## 拆分触发条件

### 自动检测指标

1. **计划步骤数量**
   - 步骤数 > 7 个：建议拆分
   - 步骤数 > 10 个：强制拆分

2. **涉及文件数量**
   - 文件数 > 15 个：建议拆分
   - 文件数 > 20 个：强制拆分

3. **时间估算**
   - 预计时间 > 4 小时：建议拆分
   - 预计时间 > 8 小时：强制拆分

4. **功能复杂度**
   - 涉及多个独立功能模块：建议拆分
   - 涉及多个技术栈（前端+后端+数据库+配置）：建议拆分

---

## 拆分策略

### 策略 1: 按功能模块拆分

**适用场景**：需求包含多个独立的功能

**示例**：
- 原始需求："实现用户注册、登录、密码重置、用户资料管理"
- 拆分后：
  - 计划1: 用户注册模块
  - 计划2: 用户登录模块
  - 计划3: 密码重置模块
  - 计划4: 用户资料管理模块

**优势**：每个模块独立、清晰、可测试

---

### 策略 2: 按技术栈拆分

**适用场景**：前端和后端工作量大且相对独立

**示例**：
- 原始需求："实现用户认证系统（包括UI和API）"
- 拆分后：
  - 计划1: 后端 API 设计和实现（认证逻辑、数据库、中间件）
  - 计划2: 前端 UI 开发（登录表单、注册页面、状态管理）

**优势**：前后端可并行开发，减少阻塞

---

### 策略 3: 按依赖关系拆分

**适用场景**：某些功能需要依赖其他功能先完成

**示例**：
- 原始需求："实现电商系统（商品管理、订单系统、支付集成）"
- 拆分后：
  - 计划1: 商品管理模块（基础数据，无依赖）
  - 计划2: 订单系统模块（依赖商品数据）
  - 计划3: 支付集成模块（依赖订单系统）

**优势**：遵循开发顺序，避免依赖问题

---

### 策略 4: 按优先级拆分

**适用场景**：需求包含多个优先级不同的功能

**示例**：
- 原始需求："实现博客系统（文章发布、评论系统、点赞、标签、搜索）"
- 拆分后：
  - 计划1 (P0): 文章发布模块（核心功能）
  - 计划2 (P1): 标签和分类（组织功能）
  - 计划3 (P2): 评论系统（交互功能）
  - 计划4 (P3): 点赞和搜索（增强功能）

**优势**：高优先级功能优先交付

## 拆分流程

### Phase 1: 规模评估

```markdown
## 计划规模评估

### 原始需求
<用户提供的原始需求>

### 规模指标
- 预计步骤数: X 步
- 涉及文件数: Y 个
- 预计耗时: Z 小时
- 功能模块数: N 个

### 拆分建议
- [ ] 不需要拆分
- [ ] 建议拆分（策略：功能模块 / 技术栈 / 依赖关系 / 优先级）
- [ ] 强制拆分（策略：功能模块 / 技术栈 / 依赖关系 / 优先级）
```

### Phase 2: 生成拆分计划

生成一个**总计划（Master Plan）**，包含：
- 总体概述
- 子计划列表
- 子计划之间的依赖关系
- 执行顺序

示例：

```markdown
## 总计划：用户认证系统

### 子计划列表

1. **计划1: 用户注册模块** (`user-registration`)
   - 优先级: P0
   - 依赖: 无
   - 预计耗时: 2 小时

2. **计划2: 用户登录模块** (`user-login`)
   - 优先级: P0
   - 依赖: 计划1
   - 预计耗时: 1.5 小时

3. **计划3: 密码重置模块** (`password-reset`)
   - 优先级: P1
   - 依赖: 计划1
   - 预计耗时: 2 小时

4. **计划4: 用户资料管理模块** (`user-profile`)
   - 优先级: P1
   - 依赖: 计划1, 计划2
   - 预计耗时: 2.5 小时

### 执行顺序
计划1 → 计划2 → {计划3, 计划4} (并行)

### 总耗时
约 6-7 小时（并行情况下）
```

### Phase 3: 生成子计划详情

为每个子计划生成独立的详细计划文件：

- `.codebuddy/plan/user-registration.md`
- `.codebuddy/plan/user-login.md`
- `.codebuddy/plan/password-reset.md`
- `.codebuddy/plan/user-profile.md`

每个子计划包含：

```markdown
## 子计划: 用户注册模块

### 概述
实现用户注册功能，包括邮箱验证、密码加密。

### 任务类型
- [x] Backend

### 实施步骤
1. 创建用户数据库模型
2. 实现注册 API 端点
3. 添加邮箱验证逻辑
4. 编写单元测试

### 关键文件
| File | Operation | Description |
|------|-----------|-------------|
| src/models/User.ts | Create | 用户模型 |
| src/api/register.ts | Create | 注册接口 |
| src/services/auth.ts | Modify | 认证服务 |

### 风险和缓解
| Risk | Mitigation |
|------|------------|
| 邮箱服务不可用 | 使用 Mock 服务用于开发 |

### 依赖
无

### 后续依赖
- 计划2: 用户登录模块
- 计划3: 密码重置模块
- 计划4: 用户资料管理模块
```

### Phase 4: 呈现给用户

```markdown
# 计划拆分完成

## 总览
原始需求规模较大，已拆分为 4 个子计划。

## 总计划文件
`.codebuddy/plan/user-authentication-master.md`

## 子计划列表
1. [计划1] 用户注册模块 - `.codebuddy/plan/user-registration.md`
2. [计划2] 用户登录模块 - `.codebuddy/plan/user-login.md`
3. [计划3] 密码重置模块 - `.codebuddy/plan/password-reset.md`
4. [计划4] 用户资料管理模块 - `.codebuddy/plan/user-profile.md`

## 执行顺序
按以下顺序执行（可并行）：
1. 先执行计划1（用户注册）
2. 再执行计划2（用户登录）
3. 然后并行执行计划3和计划4

## 下一步
- **查看总计划**: `/plan .codebuddy/plan/user-authentication-master.md`
- **执行子计划1**: `/execute .codebuddy/plan/user-registration.md`
```

---

## 执行流程

### 选项 1: 用户逐个执行

用户按照依赖顺序逐个执行子计划：

```bash
# 执行计划1
/execute .codebuddy/plan/user-registration.md

# 验证通过后，执行计划2
/execute .codebuddy/plan/user-login.md

# 并行执行计划3和计划4
/execute .codebuddy/plan/password-reset.md
/execute .codebuddy/plan/user-profile.md
```

### 选项 2: 批量执行（推荐）

用户请求批量执行所有计划：

```bash
/execute-all .codebuddy/plan/user-authentication-master.md
```

multi-execute 自动：
1. 读取总计划
2. 按照依赖顺序依次执行子计划
3. 每个子计划完成后进行验证
4. 失败时停止并报告错误

---

## 实施要点

### 1. 拆分粒度

- **过细**：增加管理成本，子计划之间协作复杂
- **过粗**：失去拆分的意义
- **推荐**：每个子计划 3-7 个步骤，2-4 小时完成

### 2. 依赖关系标注

每个子计划必须明确标注：
- 依赖的前置计划
- 被哪些后续计划依赖
- 是否可以并行执行

### 3. 数据一致性

拆分时要考虑：
- 跨子计划的数据共享（如用户模型）
- 子计划之间的接口契约
- 数据库迁移脚本的执行顺序

### 4. 测试策略

- 每个子计划完成后进行集成测试
- 所有子计划完成后进行端到端测试
- 回归测试确保不影响现有功能

## 总结

计划拆分策略能够：
1. 提升大型需求的可管理性
2. 降低单个计划的风险
3. 支持并行开发
4. 便于进度跟踪和交付

关键原则：
- 合理的拆分粒度（3-7 步骤）
- 明确的依赖关系
- 清晰的执行顺序
- 独立可验证的子计划
